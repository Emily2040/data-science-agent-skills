# Feature Store Readiness

## Executive Summary

**Feature Store Readiness** is a portable, provider-neutral data science agent skill designed to decide whether a feature store is needed and design features to avoid training-serving skew, staleness, and reuse confusion.

> **Core pain solved:** Teams either overbuild feature stores too early or underbuild shared feature governance until skew breaks models.

> **Proof callout:** Prevents both feature-store bloat and feature chaos.

## Research-Informed Design Standard

This skill follows reproducible data science and portable agent-skill standards:

- **Cookiecutter Data Science**: immutable raw data, clear artifact layout, and repeatable command entrypoints.
- **Kedro**: explicit input/output data contracts and modular workflow boundaries.
- **MLflow**: traceable parameters, metrics, provenance hashes, and governance-ready evaluation records.
- **Anthropic & Open Agent Skills**: concise `SKILL.md` frontmatter, progressive disclosure via `references/`, and deterministic local scripts in `scripts/`.
- **CfRR Reproducible Research**: deterministic verification, explicit uncertainty, and zero hidden state.

## Problem It Solves

Teams either overbuild feature stores too early or underbuild shared feature governance until skew breaks models. Without a structured gate, teams routinely discover `same feature computed differently online` or `freshness unknown` only after engineering effort or executive credibility has already been spent.

## What This Skill Should Do

- Transform a vague request into an explicit Feature Store Readiness decision with named owner, evidence, assumptions, and action threshold.
- Inspect local artifacts first: data extracts, schemas, notebooks, SQL, pipeline configs, model reports, tickets, and prior decisions.
- Separate mechanical checks from expert judgment so another reviewer can reproduce what was checked and what was inferred.
- Classify findings as stop, fix-first, monitor, accepted risk, or owner decision instead of producing generic advice.
- Preserve raw evidence and never silently mutate data, notebooks, model artifacts, or production configs.
- Return a decision artifact that can be handed to a data scientist, ML engineer, governance reviewer, or stakeholder without hidden context.

## Required Inputs

- feature list
- training data flow
- serving flow
- latency needs
- reuse demand
- ownership model

## Operating Workflow

1. Assess whether features need online serving, reuse, point-in-time correctness, or shared governance.
2. Check training-serving skew, freshness, TTL, backfill, and ownership risks.
3. Recommend no store, lightweight registry, batch feature table, or full feature store.
4. Define feature contracts and lineage requirements.
5. Return a readiness decision and migration plan.

## Expected Outputs

- feature-store decision
- skew risk table
- feature contract outline
- TTL and freshness plan
- migration steps

All outputs are delivered inside the eight-section decision contract: `Problem`, `Inputs`, `Checks performed`, `Findings`, `Decision`, `Risks`, `Next actions`, and `Artifacts`.

## Concrete Use Cases

- **Pre-commit readiness gate**: Run `scripts/online_offline_skew_check.py` on `feature list` to produce a `feature-store decision` before approving engineering scope.
- **Adversarial review**: Challenge a proposed `go` recommendation when `same feature computed differently online` or `freshness unknown` is suspected in `training data flow`.
- **Cross-team handoff**: Generate `skew risk table` and `migration steps` so ML engineers, governance reviewers, or downstream agents can act without re-running discovery.
- **Regression audit**: Score completed review checklists with `scripts/checklist_score.py --strict` inside CI to prevent unverified artifacts from shipping.

## Red Flags

- same feature computed differently online
- freshness unknown
- no point-in-time join
- feature owner unclear
- feature store proposed without reuse
