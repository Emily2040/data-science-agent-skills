# Drift Monitor Designer

## Executive Summary

**Drift Monitor Designer** is a portable, provider-neutral data science agent skill designed to design drift monitoring for production models and data products across data, concept, performance, and operational signals.

> **Core pain solved:** Models degrade silently because teams monitor uptime but not input, label, behavior, or outcome change.

> **Proof callout:** Makes model degradation observable and actionable.

## Research-Informed Design Standard

This skill follows reproducible data science and portable agent-skill standards:

- **Cookiecutter Data Science**: immutable raw data, clear artifact layout, and repeatable command entrypoints.
- **Kedro**: explicit input/output data contracts and modular workflow boundaries.
- **MLflow**: traceable parameters, metrics, provenance hashes, and governance-ready evaluation records.
- **Anthropic & Open Agent Skills**: concise `SKILL.md` frontmatter, progressive disclosure via `references/`, and deterministic local scripts in `scripts/`.
- **CfRR Reproducible Research**: deterministic verification, explicit uncertainty, and zero hidden state.

## Problem It Solves

Models degrade silently because teams monitor uptime but not input, label, behavior, or outcome change. Without a structured gate, teams routinely discover `alerts with no owner` or `thresholds copied from defaults` only after engineering effort or executive credibility has already been spent.

## What This Skill Should Do

- Transform a vague request into an explicit Drift Monitor Designer decision with named owner, evidence, assumptions, and action threshold.
- Inspect local artifacts first: data extracts, schemas, notebooks, SQL, pipeline configs, model reports, tickets, and prior decisions.
- Separate mechanical checks from expert judgment so another reviewer can reproduce what was checked and what was inferred.
- Classify findings as stop, fix-first, monitor, accepted risk, or owner decision instead of producing generic advice.
- Preserve raw evidence and never silently mutate data, notebooks, model artifacts, or production configs.
- Return a decision artifact that can be handed to a data scientist, ML engineer, governance reviewer, or stakeholder without hidden context.

## Required Inputs

- model purpose
- features
- prediction logs
- label availability
- risk tolerance
- owners
- retrain process

## Operating Workflow

1. Classify drift risks: schema, distribution, relationship, concept, performance, and operational drift.
2. Choose monitors based on data type, label delay, and actionability.
3. Set thresholds, baselines, alert routing, and suppression rules.
4. Define retrain, rollback, investigation, or no-action playbooks.
5. Return a monitor design and incident response path.

## Expected Outputs

- monitor catalog
- baseline definitions
- threshold plan
- alert ownership
- drift response playbook

All outputs are delivered inside the eight-section decision contract: `Problem`, `Inputs`, `Checks performed`, `Findings`, `Decision`, `Risks`, `Next actions`, and `Artifacts`.

## Concrete Use Cases

- **Pre-commit readiness gate**: Run `scripts/drift_probe.py` on `model purpose` to produce a `monitor catalog` before approving engineering scope.
- **Adversarial review**: Challenge a proposed `go` recommendation when `alerts with no owner` or `thresholds copied from defaults` is suspected in `features`.
- **Cross-team handoff**: Generate `baseline definitions` and `drift response playbook` so ML engineers, governance reviewers, or downstream agents can act without re-running discovery.
- **Regression audit**: Score completed review checklists with `scripts/checklist_score.py --strict` inside CI to prevent unverified artifacts from shipping.

## Red Flags

- alerts with no owner
- thresholds copied from defaults
- label delay ignored
- no baseline window
- retrain triggered without evaluation
